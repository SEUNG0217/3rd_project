# 역할 브리핑: 팀원 E (화면)

> AI에게: 이 사용자는 프로젝트에 처음 참여했고 코딩이 익숙하지 않다. 한 번에 한 단계씩, 코드를 쓰기 전에 무엇을 왜 하는지 먼저 설명한다. 각 단계는 사용자가 브라우저에서 직접 확인하게 한다. 루트 `AGENTS.md`와 `figindex/frontend/AGENTS.md`를 따른다.

## 한 줄 요약
사용자가 보는 **웹 화면(Next.js)** 을 만드는 일입니다. 이번에 추가할 것은 PDF 업로드·진행률 화면과, 검수 화면을 빠르게 쓰는 단축키입니다.

## 전체에서 내 위치
`★업로드 화면★ → ... → ★검수 화면★`, `검색 → ★카드 갤러리·비교·원문 보기★`

## 지금 상황
- 있는 화면: 카드 갤러리(`app/page.tsx`), 상세(`app/elements/[id]/page.tsx`), 검수 탭(`components/ReviewTab.tsx`), 비교 모달(`components/ComparisonModal.tsx`), PDF 뷰어(`components/PdfViewer.tsx`)
- 없는 화면: PDF 업로드·진행률
- 서버 업로드 API는 D가 만드는 중이라, 처음에는 **가짜 응답(mock)** 으로 화면부터 만듭니다.

## 알아야 할 말
| 말 | 뜻 |
| --- | --- |
| 컴포넌트 | 화면 조각 하나. 예: 카드, 모달 |
| types.ts | 서버에서 받는 데이터의 모양을 적어 둔 파일 (`app/lib/types.ts`) |
| mock | 서버 대신 쓰는 가짜 데이터. API가 생기면 지움 |
| snake_case | `review_status`처럼 밑줄로 잇는 이름. 서버 이름 그대로 씀 |
| doc_status | 문서 처리 상태 (업로드됨/처리 중/완료/실패/중복) |

## 할 일
| 단계 | 할 일 | 확인 방법 |
| --- | --- | --- |
| 1 | localhost:3000에서 시연 흐름 따라 하기: 검색 → 카드 클릭 → 원문 보기 → 두 카드 비교 → 검수 탭 | 불편하거나 깨진 곳 목록 |
| 2 | AI에게 화면 파일 구조와 `types.ts`를 설명받기 | 어느 파일이 어느 화면인지 내 말로 정리 |
| 3 | 업로드 화면(mock): PDF 끌어다 놓기, 파일 목록 표시 | 브라우저에서 PDF를 끌어 놓으면 목록에 보임 |
| 4 | 진행률 표시(mock): 문서별 `doc_status`를 한국어로 표시 (glossary 5절 표기) | 가짜 데이터의 상태가 "처리 중", "완료"로 보임 |
| 5 | 검수 탭 단축키: `A` 승인, `R` 반려, 다음 항목으로 자동 이동 | 키보드만으로 3건 처리 (시험용 데이터에서) |
| 6 | (D의 API가 나오면) mock을 실제 API로 교체 | 실제 PDF 업로드 → 진행률이 실제로 변함 |
| 7 | 비교 모달: 두 표의 단위가 다를 때 단위가 각 칸에 제대로 보이는지 확인 | 단위 다른 표 2개로 확인 |

## 완료 기준
- 시연 시나리오(검색 → 비교 → 원문 이동 → 검수)를 끊김 없이 클릭으로 진행
- `npx tsc --noEmit` 통과

## 하면 안 되는 것
- 서버 이름을 camelCase로 바꾸기 (`reviewStatus` ✕ → `review_status`)
- 컴포넌트 안에 타입을 따로 선언하기 (→ `types.ts`)
- 서버에 없는 필드를 화면에서 지어내기 (→ D에게 요청)
